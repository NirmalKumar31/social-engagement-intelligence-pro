# Independent technical and analytical audit

Project: `social-engagement-intelligence-pro`.
Date: 2026-10-25. Initial revision `4c4aca7`; revision `241c040b1baf2c27ed2c8fcb55ca218f159a7d51`
arrived during review and its new SQL/notebook workflows are included. This is a different
project from the previously audited uplift targeting engine.

## Verdict

The project runs, its headline outputs are reproducible in the existing environment, and it
implements a substantial collection of useful analytical methods. It is a credible educational
case study. Several scientific and decision claims are not yet defensible as written.

The most important problems are the unconditional launch recommendation despite a failed
guardrail; a churn model whose positive cohort mostly includes people who already quit; a
survival event-time construction that does not match the claimed event; unsupported always-valid
monitoring guarantees for the actual data design; and overprecise annual-revenue interpretation.
The dashboards and deployment artifacts also have filter/aggregation and environment issues.

There is no evidence here of fabricated output numbers. Reproducing a number does not establish
that its estimator, label, business meaning or recommendation is correct.

## S01 — Launch recommendation contradicts the stated guardrail policy

**Locations:** `sei/experiment.py:METRICS`, `sei/report.py:build_memo`,
`dashboard/app.py` executive page, `sei/pbi_report.py:build_report`, README.

The supplied brief calls churn, friend interactions, negative feedback and CTR “must not get
worse” guardrails. The saved experiment table reports for friend boost:

```text
negative-feedback rate: +8.1325%
BH-adjusted p-value:    7.74734e-15
verdict:               harm
```

The memo nevertheless always begins “ship the AI feed + friend boost ... to all eligible users.”
That text is fixed in the generator; it is not derived from a decision rule. The dashboard and
Power BI recommendation are similarly fixed. Changing the data to make friend boost harmful
would not automatically reverse the recommendation. The memo does not explicitly disclose the
negative-feedback violation in its results table.

The simulation status is disclosed in README, but it is not prominent enough in the standalone
memo and primary dashboard/report decision headers. A reader receiving only those artifacts
could mistake synthetic experimental evidence for a real product trial.

**Required correction:** define guardrail tolerances/noninferiority margins, multiplicity policy
and decision states before analysis. Either block launch on the failing criterion or explicitly
state that a named tradeoff overrides it; do not silently redefine “must not worsen.” Generate
recommendations from those states, with synthetic-data/scenario labels in every standalone
deliverable. A null, reversed-effect and guardrail-harm fixture must produce appropriate
non-launch/conditional decisions. Non-significance alone must not be treated as proof of safety.

## S02 — The churn model mostly detects departures that already happened

**Locations:** `sei/retention.py:93–100`, `simulate.py` absorbing `alive` process.

Feature timestamps are correctly restricted through day 13; this audit did not find the old
target-column leakage in the supplied walkthrough. The cohort/target interpretation is still
wrong for the claimed incident-churn early-warning use case.

Being active at least once on days 7–13 does not imply a user is still alive at the end of day 13.
Comparing the existing labels with the simulator's held-aside latent quit time gives:

| Positive target cases in the scoring cohort | Count |
|---|---:|
| All future-inactivity positives | 1,501 |
| Already latently quit by day 13 | **1,013 (67.49%)** |
| Quit during days 14–27 | 419 |
| Never latently quit during the simulation | 69 |

Among the OOF highest-risk 10%, 1,021 positives are captured; **833** of those already quit by
day 13. Recency can therefore perform extremely well by recognizing existing departures. AUC
0.896 is a valid score for the defined future-inactivity classification task, but not evidence
of equivalent ability to predict preventable new departures.

**Required correction:** choose the intended task explicitly: incident churn, inactivity
forecasting, or win-back/reengagement. Use latent status only as a clearly marked simulator
validation benchmark, never as a production feature. For incident-churn benchmarking, score an
appropriate at-risk population and distinguish preexisting departure from new events. For a
log-only operational task, use observable eligibility and label the target honestly. Reassess
AUC, PR-AUC, calibration and campaign value for the actual intervention population.

Also compare logistic regression fairly: its `class_weight="balanced"` deliberately changes
probability calibration for a ~2.6% outcome. Include an unweighted and/or equivalently calibrated
logistic baseline before concluding that the model family itself has “terrible calibration.”

## S03 — Cox and Kaplan–Meier event times are constructed inconsistently

**Locations:** `features.py:build_user_table`, `retention.py:36–55`.

The event indicator means no activity in the final seven days. An event time is then assigned as
`last_active_day + 1`; everyone else is censored at day 28. All modeled events consequently occur
by day **21**, followed by a mechanically event-free risk period through day 28. Final-window
inactivity is not a directly observed irreversible quit timestamp.

Diagnostic comparison to the simulator:

- Observed final-window “churn”: **5,355**.
- Latent departures across the full 28 days: **5,652**.
- Observed churn without any latent departure: **612**.
- Latent departures not counted as observed churn: **909**.

These are not necessarily bad labels for a binary inactivity endpoint. They do not justify
interpreting the fitted Cox ratio as a clean instantaneous risk ratio for permanent quitting, or
transporting it directly into a 12-month permanent-attrition forecast.

**Required correction:** define event detection, event time, observation horizon and censoring
jointly. Options include time to a first confirmed inactivity episode, a recurrence/reactivation
model, a properly censored terminal-gap endpoint, or a separate oracle survival benchmark using
simulator departure times. Explain what is observable at each time. Assess proportional-hazards
adequacy and show restricted-horizon survival differences where more appropriate. Recompute the
impact model only after its hazard input has a justified meaning. See [lifelines' data and Cox
model documentation](https://lifelines.readthedocs.io/en/latest/Survival%20Regression.html).

## S04 — Sequential inference is not demonstrated to be always valid for this design

**Locations:** `stats.py:129–138`, `experiment.py:163–201`, sequential test in `tests/test_stats.py`.

The formula is a normal-mixture likelihood-ratio construction. A likelihood-ratio expression
does not become an always-valid process merely by inserting arbitrary running estimates and
estimated standard errors.

The reported null simulation and regression test add **new independent Gaussian users every
day with known variance**. The actual application repeatedly observes the same fixed users,
with latent heterogeneity, AR activity, dropout, and a time-varying treatment effect. The code
does not establish the required sequential likelihood/martingale conditions for those cumulative
user averages. Its mixing scale also uses the **day-27 control mean** even when reporting day-0
monitoring, so it is not fixed in advance from information available at the look.

An audit-only null diagnostic that re-randomizes the existing control users (500 splits, seed
812) gave naive any-look rejection **13.6%**, mixture rejection **1.4%**, fixed-horizon rejection
**5.0%**. This does not show an anti-conservative mixture monitor in this dataset. It does show
that the advertised 27%/0.9% experiment is a different design, and a limited conservative
diagnostic is not a universal guarantee. The implemented monitor also covers minutes, not all
the churn/friend-interaction guardrails proposed in the rollout instructions.

**Required correction:** predefine the estimand, sampling unit, filtration, prior scale and
stopping rule. Use an appropriate sequential method for the actual design, or label the current
monitor an approximation/demo without an always-valid guarantee. Test serial dependence,
heavy-tailed activity, dropout, multiple arms and guardrails under the complete monitoring rule,
including power. Do not estimate a supposedly prespecified prior from future observations.
Reference: [Johari et al., Always Valid Inference](https://pubsonline.informs.org/doi/10.1287/opre.2021.2135).

## S05 — Annual revenue confidence is conditional on a fragile model

**Locations:** `impact.py:21–64`, `hte.py:outcome`, dashboard business simulator and memo.

The $103M/$57M outputs reproduce exactly. They are scenario-model outputs, not identified
12-month causal revenue effects or a 99.97% empirically established launch-win probability.

Important assumptions and omitted uncertainty:

1. Revenue lift is an **unconditional late-period per-assigned-user** effect, already affected
   by inactivity/attrition. The baseline rate is instead taken from control users selected for
   not being churned, then a separate survival multiplier is applied. The decomposition needs a
   joint revenue/retention estimand to avoid overlapping attrition effects or incompatible
   survivor conditioning. This audit does not claim a uniquely quantified double-counting bias;
   the current decomposition is not justified sufficiently to identify its interpretation.
2. The Cox input inherits S03 and is transported from a 28-day constructed endpoint to a
   permanent monthly hazard effect at an assumed 3.5% baseline rate.
3. Revenue and hazard parameters are sampled independently, and treatment contrasts sharing
   the same control arm are also sampled independently. Their joint covariance is ignored.
4. Baseline revenue, parameter transport, effect persistence, population mix, changing churn
   dynamics and model-form uncertainty are not included in the displayed interval.
5. The HTE module uses another endpoint, `365 × late revenue − churn × $38`. The $38 is described
   as foregone ad-revenue LTV while late revenue already reflects inactivity. Treat this as an
   explicitly assumed utility score unless a non-overlapping economic decomposition is supplied.
   Its “annual dollars” are not directly interchangeable with the Monte Carlo cohort revenue.

The one-way sensitivity statement is true within the ranges shown, but it is not general
robustness. For illustration, jointly using the AI lift's upper marginal 95% bound, friend boost
lift's lower bound, AI HR's lower bound, friend boost HR's upper bound and 2% monthly churn
changes friend-boost minus AI value from **+$46.34M to −$26.94M**. This is a stress scenario within
individual marginal bounds, not a simultaneous 95% region or a probability estimate.

**Required correction:** specify a coherent observable economic endpoint and forecast model;
estimate joint parameter uncertainty using shared user/arm resamples and a joint survival fit
where appropriate; separately expose persistence, baseline and model-form scenarios. Label
Monte Carlo probabilities as fractions under those assumptions. Show joint stress tests and
reassess all dollars after survival/cohort fixes. A 90-day holdback should validate the model,
not be described as optional confirmation of an already-known annual effect.

## S06 — Retention policy is optimized on the test set and can choose guaranteed losses

**Locations:** `retention.py:142–158`, `dashboard/app.py:291–305`.

The model is fitted without the test labels, which is good. But the “optimal” target depth and
$2.53M claim are selected by maximizing realized profit over **100 depths on those test labels**.
The chosen policy is therefore not evaluated on an untouched evaluation sample. There is no
uncertainty interval on policy value or the selected optimum, and no no-send option in the grid.

Reproduced slider case: cost **$3**, assumed save fraction **5%**, saved-user LTV **$5**. Even a
known churner is worth at most $0.25 against a $3 cost. Every campaign loses money. The dashboard
still recommends top **1%**, losing approximately **$1.089M**, while no targeting would yield $0.

Risk prediction also does not identify who is persuadable by a nudge. The fixed 18% save fraction
is a documented assumption, not learned intervention efficacy, and S02 changes what “saving”
means for many targets.

**Required correction:** choose threshold/depth on training/calibration data or use a predefined
economic probability rule, then evaluate the frozen rule elsewhere. Include no-send at zero
value, paired value uncertainty, assumptions about intervention effect and an experimental
holdout design for measuring actual efficacy. Add the adverse-slider case as a regression test.

## S07 — The purported CATE ground truth does not match the fitted outcome

**Locations:** `simulate.py` truth table, `hte.py:124–131`.

The comparison named `spearman_vs_truth_*` uses:

```python
steady_minutes_multiplier * pre_revenue * 365 - (hazard_multiplier - 1) * LTV * 0.08
```

The simulator stores latent parameters and factual quit time, not the true counterfactual
expected outcome under each arm. Actual modeled outcomes also depend on activity probabilities,
time-varying social effects, finite-horizon mortality, novelty, revenue mechanics and the
observed inactivity-label rule. The constant 0.08 is not each user's baseline event probability.

This is an approximate proxy for ordering, not exact ground-truth CATE validation. It can be
useful if labeled honestly, but does not establish effect recovery/calibration for `outcome()`.

**Required correction:** either rename it a latent-parameter proxy correlation, or compute
counterfactual expectations under the same outcome definition using analytical calculations or
repeated all-arm simulations with controlled/common random numbers. Report approximation Monte
Carlo error, effect bias/RMSE/calibration and policy regret versus a correct oracle. Keep oracle
information out of fitted features and selection.

## S08 — Power BI control measures conflict with arm-label filters

**Locations:** `powerbi.py:164–170`, report `ARM = dim_arm[arm_label]` and Engagement Trends.

The report's series filter is `dim_arm[arm_label]`, whereas control measures only apply
`dim_arm[arm] = "control"`. Under a treatment-label context these constraints intersect to an
empty arm table. Replacing a filter on `arm` does not automatically clear the distinct
`arm_label` filter. The empty denominator can produce blank or misleading derived lift values.

This is a source-derived semantic defect supported by the [documented CALCULATE filter
behavior](https://learn.microsoft.com/en-us/dax/calculate-function-dax), not a claim that this
audit observed the live Fabric chart display a particular number. A local dimension-table
intersection confirms zero candidate control rows for either treatment label.

**Required correction:** explicitly remove relevant arm-dimension filters when evaluating the
control baseline, then select control, preserving date and matched segment context. Validate in
the semantic engine against pandas reference results for each arm, label/key filter, segment,
date range and slicer combination. Test control's own lift is zero and treatment baseline is
nonempty. Do not equate a visual rendering successfully with a correct DAX result.

## S09 — Dependency promises do not match supported execution

**Locations:** requirements files, Makefile setup, `powerbi.py:126–133` and `export_data`.

`make setup` installs open-ended requirements, not `requirements-lock.txt`. A concrete allowed
configuration is pandas **3.1.0**, whose inferred string dtype causes:

```text
_dtype(pd.Series(['control', 'ai_feed']))
TypeError: Cannot interpret '<StringDtype(na_value=nan)>' as a data type
```

`export_data` also uses NumPy subtype checks on pandas dtypes. The current environment succeeds
because it uses pandas 2.3.3. NumPy >=1.26 is advertised even though HTE calls `np.trapezoid`, an
API introduced in NumPy 2.0. Recent Streamlit usage likewise needs minimum-version verification,
not an assumption that all declared lower versions work.

**Required correction:** use pandas dtype predicates supporting extension dtypes; test the
actual minimums and latest supported range; make reproducible setup use a maintained lock or
equivalent constraints and document interpreter/system dependencies. Run clean installation plus
the pipeline/export, not only tests in an existing environment. The later SQL commit already
adds openpyxl and its other direct dependencies, so missing openpyxl is **not** an outstanding
finding against the final revision.

## S10 — CUPED's relative lift uses the wrong documented denominator

**Location:** `stats.py:37–53`.

`cuped` obtains relative lift/SE from adjusted arm means, then overwrites `mean_control` and
`mean_treatment` with raw means without recalculating the relative result. Thus `rel_lift` is
not `diff / mean_control`, despite the docstring promising a raw-control denominator.

In the current AI result, reported relative lift is **0.11560085**, while adjusted difference
divided by reported raw control mean is **0.11545734**. This is a small current-data discrepancy,
not a claim that the primary effect vanishes. A deliberately imbalanced small fixture produces
0.008822 versus 0.012602 and demonstrates the contract error clearly.

**Required correction:** define the ratio estimand explicitly and calculate its joint
uncertainty correctly, including numerator/denominator dependence after adjustment. Keep raw and
adjusted means separately named. The helper named `welch` also uses normal critical values and
normal-tail p-values, not Welch–Satterthwaite degrees of freedom. This approximation is reasonable
at ~20k per arm, but should be named or implemented accurately and handle small/degenerate data.

## S11 — Policy comparison and Qini terminology need stronger definitions

**Locations:** `hte.py:68–91`, policy evaluation/plotting and report.

The train/test separation and internally cross-fitted DR nuisance models are useful. Remaining
limitations:

- “Model-targeted beats blanket, but CIs overlap” is not a statistical comparison. Compute the
  paired **difference** directly. Reusing saved test predictions, this audit obtains model
  minus friend boost **+$0.1387/user**, approximate paired 95% interval **[−$0.7316, +$1.2026]**,
  bootstrap positive fraction **0.64** (400 draws, existing function seed 0). It is appropriately
  exploratory and does not establish superiority.
- `ipw_policy_value` is self-normalized/Hájek estimation, with finite-sample properties distinct
  from an unbiased Horvitz–Thompson estimate. Use the known randomization probability 1/3 unless
  explicitly justifying an estimated propensity and its uncertainty.
- The plotted “Qini” is a cumulative full-population uplift-gain curve for a continuous utility,
  without an origin point. Its reported AUC divided by random area is not standard normalized
  Qini, and can be unstable when the random gain is near zero or negative. State the convention
  and test its behavior; do not compare its ratio to unrelated literature Qini scores.
- The readable tree is fitted to predictions on the test cohort; it is a surrogate explanation,
  not an independently evaluated deployable tree policy.

**Required correction:** use explicit utility/scenario units (S05), paired policy differences,
appropriate randomization weights and robust bootstrap support checks. Freeze policies before
evaluating them. If deploying the tree, train it without evaluation-cohort access and assess its
own policy value separately. Preserve the current caution that personalization needs a new test.

## S12 — Virality evaluation has unresolved temporal leakage/provenance

**Location:** `virality.py:42–63`; UCI feature definitions.

The target threshold is calculated on **all** shares before the split: **2,800** versus
**2,900** using training articles alone. Thus a supposed future prediction task uses future
outcome distribution information to define its target.

Training and test dates also overlap at **2014-07-27**, containing 29 boundary-date articles.
More fundamentally, keyword share aggregates and referenced-article share features lack verified
publication-time availability. The largest drivers include `kw_avg_avg` and
`self_reference_min_shares`. UCI describes a single acquisition date of **2015-01-08**, so merely
sorting article dates does not establish that training labels/aggregates were available when the
test articles were published. This is an unresolved point-in-time validity risk, not proof that
every such feature necessarily leaks. [Official dataset documentation](https://archive.ics.uci.edu/dataset/332/online%2Bnews%2Bpopularity).

The “creator playbook” uses unadjusted associations over the full dataset; weekend/channel
differences are not causal effects of changing publication strategy.

**Required correction:** define the popularity horizon and target using training information or
a prespecified business threshold; split on whole dates; document feature/label availability
and perform ablations excluding unverifiable popularity aggregates. If provenance cannot support
a production-style evaluation, call it an ordered retrospective benchmark. Keep creator advice
descriptive and contextual, with support/uncertainty and appropriate controlled follow-up.

## S13 — Exposure conclusions are built into the simulated ranker

**Location:** `nlp.py:exposure_simulation`, memo content-health section.

Sentiment modeling genuinely uses the official train/validation/test structure, with vocabulary
fit on training only and C selected on validation. The reproduced macro-recall comparison is a
useful benchmark. [TweetEval documentation](https://github.com/cardiffnlp/tweeteval) supports
those fixed splits.

The exposure experiment is different: engagement score explicitly weights predicted negative
sentiment at 0.9 versus positive at 0.3; the AI ranker is assigned stronger engagement weighting
and topic concentration; expected engagement also explicitly rewards negativity. No real
engagement data trains that relationship. “The algorithm learns outrage drives engagement” is
therefore a built-in scenario, not a discovered real-data mechanism. Applying the classifier to
its own training posts for the exposure pool also mixes in-sample and held-out measurement.

**Required correction:** label the result as “under assumed ranker weights, concentration and
negative-sentiment preference.” Show parameter sensitivity, use held-out/human labels or OOF
sentiment predictions for a measurement check, and avoid equating negative sentiment with
toxicity/polarization. Keep the current simulation caveat directly beside prominent percentages.
Do not use these simulated harms as independent empirical evidence about a real feed.

## S14 — Power BI report semantics and refresh are incomplete

**Locations:** `powerbi.py:RELATIONSHIPS`, `pbi_report.py:build_report`, Fabric notebook.

- `cate_deciles` has no arm relationship. Its calibration chart sums predicted and observed
  CATEs over the two treatment arms by decile, with no arm series/filter separating them.
  Different treatment effects are not additive observations of one effect.
- Qini has a fact-table arm slicer but no common arm relationship to the CATE table. With no
  selection, Qini also sums the two arms' gains by model/fraction. Make per-arm identity explicit.
- Some precomputed outputs are overall estimates and do not follow daily-fact segment slicers.
  Label their population and prohibit misleading cross-filter expectations; do not sum CIs or
  rates as though they were additive measures.
- Fixed report prose says friend boost “lowers churn in every age group.” The 55+ point estimate
  is actually **+1.193 percentage points**, adjusted p **0.3455**. This is not evidence of harm,
  but it does contradict that blanket factual statement. “Mostly novelty” also overstates the
  observed average attenuation: 7.7% of the original 11.6% remains in the fitted extrapolation.
- Regenerating CSVs does not regenerate fixed report narrative text in an already deployed
  report. The Fabric notebook skips the semantic model when its name already exists, so reruns
  do not update changed model tables/relationships/measures. A data refresh is not a schema
  migration.

**Required correction:** add shared dimensions where appropriate, preserve arm identity, define
nonadditive measures, test slicer behavior in Fabric/Desktop and compare with Python references.
Generate narrative from a versioned results artifact, including uncertainty and synthetic status.
Make semantic-model deployment update-aware and validate model/report/data schema versions
together. Pin a coherent artifact revision for refresh rather than independently reading mutable
`main` files with no run manifest. No live model was changed in this audit.

## S15 — Novelty asymptote is not a measured steady state

**Location:** `experiment.py:daily_dynamics`.

An unweighted exponential curve is fitted to 28 correlated daily ratios. The fit covariance is
discarded, serial user dependence and the shared control are not propagated, and no interval is
reported for asymptote or decay time. Ongoing attrition and social-affinity ramp effects also
change the time series; a single exponential does not isolate novelty causally.

The impact model uses late-window revenue, not an independently validated asymptotic revenue
effect. A four-week descriptive fit cannot establish persistence over twelve months.

**Required correction:** call these fitted asymptotic/extrapolated parameters; bootstrap whole
users with shared arm draws for curves/fit intervals; assess model-form and window sensitivity;
show observed week-4 effects separately. Use a longer holdback or a validated persistence model
before presenting a stable long-run effect.

## S16 — Engineering and tests need targeted expansion

**Locations:** pipeline/download/config modules, Makefile, tests, dashboard caches and SQL helper.

Current strengths: simple module boundaries, deterministic seed, user-grain ITT aggregation,
real-data benchmarks, accessible local execution and 13 passing checks. Remaining gaps:

- No CI workflow is present. Five data-contract tests skip when generated user data is absent;
  a fresh checkout's successful remaining unit tests do not verify its pipeline.
- The leakage test checks nonnegative recency and column naming rather than perturbing future
  data and proving every feature/cohort input is unchanged.
- The A/A check calibrates a raw mean test, not the full CUPED/multiple-arm/decision/guardrail
  pipeline. The sequential test covers the independent-Gaussian toy design only.
- External files are downloaded from mutable locations without content manifests or pinned
  TweetEval revision. Existing files are trusted. There is no source/config/data/environment
  identity tying every output to one run.
- Pipeline stages overwrite final locations in place, Power BI directories are deleted before
  rewrite, warnings are globally suppressed, and `--skip-nlp` trusts whatever older outputs
  exist. Interrupted or mismatched runs can leave a coherent-looking mixture of generations.
- Streamlit caches are keyed by file name only, so rebuilt outputs can remain stale until cache
  invalidation. The SQL connection similarly captures its view inventory only once.
- The default pipeline always simulates users; replacing files with real experiment logs is
  not an implemented supported input mode. Schema/cohort/time metadata and quality checks are
  needed before promising “replace the logs and everything runs.”

**Required correction:** add a small raw fixture and complete isolated pipeline test in CI;
target regressions from this audit; pin or fingerprint inputs and record run metadata; stage
outputs before promotion; validate skipped-stage compatibility; surface important warnings;
invalidate caches by run identity/fingerprints. Add a defined real-data ingestion mode only if
claiming support for it. Keep these changes proportionate to a case study rather than adding
unnecessary infrastructure.

## Recommended implementation order

1. Correct synthetic-data labels, decision wording and the failed negative-feedback guardrail.
2. Redefine the churn cohort/target and survival endpoint; rerun those analyses before any
   campaign or twelve-month claim is updated.
3. Validate or qualify sequential monitoring, define coherent economic endpoints, and add
   joint/persistence scenario uncertainty. Preserve the current outputs as historical evidence.
4. Fix no-send/test-selected retention policy, CATE truth validation, CUPED relative inference
   and direct paired policy comparisons.
5. Repair Power BI filters/aggregation/refresh, dependency compatibility and reproducible setup.
6. Address temporal feature provenance in virality, conditional ranker-exposure wording and
   novelty uncertainty.
7. Add targeted CI/regression tests, run manifests and output/cache consistency checks, then
   regenerate all artifacts together and report revised results without requiring them to stay
   favorable.

Completion should be documented per S01–S16: changed files, actual checks, revised numbers,
remaining assumptions, and whether the live Fabric model was truly tested. Do not silently
delete this audit, optimize against repeated held-out results, or describe a new random split of
the same inspected data as independent confirmation. No push or live deployment is authorized
by this audit request.
